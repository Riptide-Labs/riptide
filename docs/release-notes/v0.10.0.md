# Riptide 0.10.0 — rollups tell you when they are stale

Draft for `gh release edit v0.10.0 --notes-file docs/release-notes/v0.10.0.md` (see RELEASING.md). One line per bullet; GFM renders newlines as breaks.

## Action required on upgrade

### Does this affect you?

Only if riptide connects to ClickHouse as a user created by `riptide onboard` — a `writer_<tenant>` user holding the shared `flow_writer` role. Check `riptide.clickhouse.username` in your config.

- Connects as `default`, or any other broadly privileged user: **nothing to do**.
- Runs with `riptide.clickhouse.manage-schema: true`: **nothing to do**.
- Connects as a `writer_<tenant>` user: apply one of the two fixes below.

If you skip it, riptide logs `Rollup <name> could not be verified` for each of the four rollups on every start, and says which grant is missing. Ingestion is unaffected, queries are unaffected, and the rollups keep serving — only the new shape check is unavailable. Nothing degrades; it just cannot confirm anything.

### Fix A — apply the grants directly

Four statements, run as a ClickHouse admin. No secrets needed, and `flow_writer` is a shared role so this covers every tenant at once. Replace `riptide` if your database is named differently:

```sql
GRANT SHOW TABLES ON `riptide`.flows_by_application_1m_mv TO flow_writer;
GRANT SHOW TABLES ON `riptide`.flows_by_conversation_1m_mv TO flow_writer;
GRANT SHOW TABLES ON `riptide`.flows_by_exporter_iface_1m_mv TO flow_writer;
GRANT SHOW TABLES ON `riptide`.flows_by_geo_asn_1m_mv TO flow_writer;
```

The check runs at startup, so restart riptide (`systemctl restart riptide`) or wait for the next one.

### Fix B — re-run `onboard`

Re-running `onboard` for any **one** tenant applies the same grants, because they live in the shared-role step rather than the per-tenant one. It also reconciles that tenant's passwords from the secrets you pass, so pass the same ones you provisioned with. A secret is a plain literal, `env://VAR`, or `file:///path[#key]`.

**DEB / RPM** — the packages install no `riptide` wrapper; the jar is invoked directly:

```bash
java -jar /usr/share/riptide/riptide.jar onboard \
  --admin-url http://clickhouse.example:8123 \
  --admin-user default \
  --admin-password 'env://CH_ADMIN_PASSWORD' \
  --tenant acme --org acme-eu \
  --writer-secret 'env://RIPTIDE_WRITER_SECRET' \
  --reader-secret 'env://RIPTIDE_READER_SECRET'
```

**Docker** — the image's entrypoint is `java`, so the `-jar` argument is passed explicitly:

```bash
docker run --rm \
  -e CH_ADMIN_PASSWORD -e RIPTIDE_WRITER_SECRET -e RIPTIDE_READER_SECRET \
  ghcr.io/riptide-labs/riptide:0.10.0 \
  -jar /app/riptide.jar onboard \
  --admin-url http://clickhouse.example:8123 \
  --admin-user default \
  --admin-password 'env://CH_ADMIN_PASSWORD' \
  --tenant acme --org acme-eu \
  --writer-secret 'env://RIPTIDE_WRITER_SECRET' \
  --reader-secret 'env://RIPTIDE_READER_SECRET'
```

**NixOS / Nix** — the Nix package does provide a `riptide` binary:

```bash
nix run github:Riptide-Labs/riptide/v0.10.0 -- onboard \
  --admin-url http://clickhouse.example:8123 \
  --admin-user default \
  --admin-password 'env://CH_ADMIN_PASSWORD' \
  --tenant acme --org acme-eu \
  --writer-secret 'env://RIPTIDE_WRITER_SECRET' \
  --reader-secret 'env://RIPTIDE_READER_SECRET'
```

On a host where the module is enabled, `services.riptide.package` is the same derivation — add it to `environment.systemPackages` if you want `riptide onboard` on the PATH instead.

Add `--database <name>` to any of these if your database is not `riptide`.

### Why `SHOW TABLES` and not `SELECT`

A row policy attached to a rollup target does **not** apply when the same rows are read through that target's materialized view. Probed on ClickHouse 26.7: a writer holding `SELECT` on the `_mv` reads every tenant's rows, while the same user is denied outright on the target the policy is attached to. Since `flow_writer` is shared by every per-tenant writer, a `SELECT` grant there would be a cross-tenant read path around the policy. `SHOW TABLES` makes the view visible to the shape check and grants no data access at all.

## Rollups notice when they are stale

`CREATE MATERIALIZED VIEW IF NOT EXISTS` does nothing against a view that already exists, so any deployment that had started riptide once kept its original rollup shape indefinitely. A rollup gaining a dimension or a measure in a new release reached a fresh install and not an upgraded one, and nothing failed or logged. Worse, the query router sent every query wider than its threshold to that rollup, so a stale rollup did not merely exist — it answered.

Riptide now compares every rollup against the shape the running version intends, at startup, in both schema modes. It compares the target's columns and their types against what the version expects, and the materialized view's stored `SELECT` against the one the version emits — the second catches a corrected aggregate, which keeps its column name and is invisible to any column comparison.

A rollup that differs is named in a warning and declined at routing time; long-range queries are answered from raw `flows` instead, and the other rollups keep serving. Startup is never failed: a stale `flows` table breaks every insert and must fail fast, but a stale rollup leaves ingestion untouched, and stopping collection to protect a query-path optimisation would trade the irreplaceable for the replaceable.

**The fallback is bounded by raw retention, and this is worth knowing before you meet it.** Raw `flows` is kept 30 days by default against the rollups' 365. A query that falls back and reaches further back than the raw retention comes back incomplete, not merely slower — it returns the rows that still exist and says nothing about the rest. Treat a declined rollup as something to repair, not to live with. The [ClickHouse configuration guide](https://riptide.space/docs/configuration/clickhouse) has the manual recreate and what it costs.

Three outcomes are reported, and they mean different things. `does not match this version's schema` is drift. `could not be verified` means riptide could not read the view definition — usually the grant above — and the rollup stays in use, because a rollup that has not been checked is not one known to be wrong. `cannot be reached` means the target table is absent or ungranted, and the rollup is declined because a query routed there would fail outright.

No repair is attempted. Riptide alters nothing, drops nothing, and creates nothing in response to drift.

## Primary keys are declared, not derived

Rollup and `flows` DDL now declare `PRIMARY KEY` explicitly instead of letting ClickHouse derive it from `ORDER BY`. Nothing changes on any deployment: the declared value is what every install already has, and pre-existing tables are untouched.

It matters for what comes next. `ALTER TABLE … MODIFY ORDER BY` appends to the *sorting* key and leaves the primary key alone, so the first time a rollup gains a dimension, an upgraded install would end up with an N-column primary key under an N+1-column sorting key while a fresh install derived N+1 for both. Nothing in a column-name or type comparison can see that difference. Declaring the key now, while every install agrees, is what keeps them agreeing later.

If you are curious whether your deployment is affected: it is not, today, and this release is what ensures it stays that way.

## Fixes

- Management HTTP requests and the shutdown path are now bounded, so a slow or stalled client cannot hold the endpoint open indefinitely, and shutdown no longer waits on it (#569, closes #545 and #564).
- Parser gauges follow the live parser and stop reporting when it stops. Previously a stopped parser's gauges kept publishing their last values, which read as a running parser (#570, closes #546).
- The deb and rpm packages now report one consistent SBOM originator instead of two different ones (#568).

## Upgrading

No configuration changes. No schema migration. No data is rewritten and no aggregation is interrupted.

The only manual step is the grant described in [Action required on upgrade](#action-required-on-upgrade), and only for deployments whose collector connects as a `writer_<tenant>` user.
