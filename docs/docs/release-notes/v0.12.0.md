## Highlights

**Rollups carry the flow protocol** (#606, closes #583). sFlow scales its counters at ingest and still reports its rate, so multiplying an sFlow row by its sampling interval double-counts it. No rollup carried the column that distinguishes it, so `SUM(bytes * samplingInterval)` — expressible against rollups since v0.11.0 — was only *correct* where sFlow was absent. `flowProtocol` is now a dimension on all four rollups, and the same scaling expression works against either table.

**The exclusion query is now documented as the subset it is.** `WHERE flowProtocol != 'SFLOW'` returns corrected volume of the NetFlow/IPFIX subset, short by every sFlow byte received, not total corrected volume. v0.11.0's documentation was explicit that the rollup form was unavailable on mixed deployments and that the correction had to be done against raw `flows`; what it did not say is that the exclusion it recommended answers a narrower question than the one being asked. The corrected total is now `sum(bytes * if(flowProtocol = 'SFLOW', 1, samplingInterval))`, and the exclusion is labelled as a subset query.

> **Corrected 2026-08-26.** This paragraph originally said earlier versions "documented a subset query as the corrected total". That was unfair: v0.11.0's docs carried a prominent warning that the query was only correct in the absence of sFlow.

**IPFIX sampling advertisements are read whatever scope they arrive under** (#604, #597, #595, closes #589 follow-ups; #594). An exporter that states its rate in a Selector Report, or under a scope riptide did not previously look in, was recorded as unsampled and under-reported by its full sampling rate. A learned rate also survives past any exporter's refresh interval rather than expiring between advertisements.

**A suffixed Kubernetes Service no longer crash-loops every collector in the namespace** (#616, closes #612 and #613). Kubernetes injects `{SVCNAME}_PORT` for every Service, and the legacy-key guard's exemption pattern absorbed the field name it was documented as unable to absorb. Any Service whose name carried a suffix took the pods down. The same fix also stops five legacy node shapes being silently waved through; see Upgrading.

**MCP answers say how far back the table behind them reaches** (#621, closes #609). A short answer no longer reads like a complete one when the table could not cover the range asked for.

## Fixes

- The converter reports a domain-pinned node that overlaps another polled range, instead of emitting a configuration whose polling split is silent (#618).
- The converter guards on what 0.9 actually binds rather than on what the converter maps, so a half-flattened file no longer drops its polling cadence (#617).
- sFlow refuses a frame length no frame could have, rather than recording it (#605).
- Dependency updates across the Maven, Docker and Actions ecosystems (#600, #601, #602, #603).

## Upgrading

**Manage-mode deployments** (`manage-schema: true`, the default) repair their rollups on the next start and need nothing.

**Provisioned deployments** (`manage-schema: false`) need two steps, and the second is easy to miss:

```bash
riptide onboard --admin-url <url> --database <db> --tenant <t> --org <o> \
  --writer-secret <ref> --reader-secret <ref>

systemctl restart riptide      # on each collector
```

Which rollups are usable is decided once at startup, so a collector that declined them keeps answering from raw `flows` until it restarts, however complete the repair was. Until both steps run, a query using `flowProtocol` against a rollup fails with `UNKNOWN_IDENTIFIER`, and every query spanning an hour or more falls back to raw `flows` and is silently truncated at raw retention.

**A corrected-volume query against a rollup now needs two boundary predicates, not one.** `samplingInterval` shipped in v0.11.0 and `flowProtocol` appends after it, so a band of rows knows its rate and not its protocol. Those rows satisfy `'' != 'SFLOW'`, so filtering on the rate alone readmits them:

```sql
SELECT sum(bytes * if(flowProtocol = 'SFLOW', 1, samplingInterval)) AS corrected_bytes
FROM riptide.flows_by_conversation_1m
WHERE timestamp >= now() - INTERVAL 90 DAY
  AND samplingInterval > 0     -- excludes rows aggregated before the rate was carried
  AND flowProtocol != '';      -- excludes rows aggregated before the protocol was carried
```

Against raw `flows` the same scaling expression needs no boundary predicates at all. Do not copy the rollup's `WHERE` clause onto raw `flows`.

**A few legacy environment shapes that 0.11 ignored will now refuse to start.**

> **Corrected 2026-08-26.** This paragraph originally said the flag-day guard "was not running at startup at all" on 0.11 and that a container carrying `RIPTIDE_NODES_*` "booted clean". That was wrong. The guard ran, and an ordinary `RIPTIDE_NODES_*` config already failed startup on 0.11. What follows is the actual difference, measured by running both releases' code over the 30 shapes `LegacyNodesFlagDayCheckTest` enumerates.

An ordinary 0.8 config in the environment failed startup on 0.11 and fails on 0.12. Nothing changes for you.

What changes is a narrow set of node names. A node whose key ends in a shape the platform also generates was silently ignored on 0.11, so its device configuration reached nothing while riptide booted clean. Those now refuse:

```
RIPTIDE_NODES_EDGE_SERVICE_PORT_SUBNET_ADDRESS     a node named edge-service-port
RIPTIDE_NODES_EDGE_SERVICE_PORT_SUBNETADDRESS      …in its relaxed-binding spelling
RIPTIDE_NODES_MGMT_SERVICE_PORT_SNMP_COMMUNITY     a node named mgmt-service-port
RIPTIDE_NODES_SVC_SERVICE_PORT_INTERFACES_1_NAME   a node named svc-service-port
RIPTIDE_NODES_PORT_1_TCP_SUBNET_ADDRESS            a node named port-1-tcp
```

If riptide starts refusing after this upgrade and it did not before, this is why: that node was never being read. Run `riptide convert` against the 0.8 configuration.

The reverse also changed, and it is the fix in the Highlights: `{SVCNAME}_PORT` for a Service named `riptide-nodes-headless`, `-metrics` or `-snmp` crash-looped every pod on 0.11 and boots on 0.12.

**If you receive sampled IPFIX from exporters that advertise their rate**, more of those advertisements are now read, so sampling-corrected volume changes for them. Raw `bytes` and `packets` are untouched, since riptide has never scaled counters at ingest, and `samplingProvenance` moves off `assumed` for the exporters concerned.

**Rolling back to 0.11.x needs no preparation, and you should not drop the rollup views.**

> **Corrected 2026-08-26.** This paragraph originally said a rollback "requires dropping the rollup views first" and told you to drop the four `_mv` objects. **That was wrong, and following it is what causes the corruption it claimed to avoid.** The same wrong advice appears in v0.11.0's notes and has been corrected there too.

An older riptide refuses to shrink a sorting key, so the target keeps every column. It also refuses to narrow the materialized view: `planViewRepair` treats a view selecting columns it does not know as a downgrade and declines it, which `RollupRepairIT.aViewFromANewerVersionIsLeftAloneRatherThanNarrowed` pins against a real server. Versions before v0.10.0 had no `MODIFY QUERY` at all, so they cannot re-point a view either. The wide view stays in place, `CREATE … IF NOT EXISTS` no-ops over it, and aggregation continues correctly into columns the running version does not read.

Dropping the views inverts that. A version that declines to build a view for a rollup it considers drifted stops feeding that rollup entirely, and a version old enough to create its own narrow view would point it at the still-wide target, writing the reserved value into a sorting-key column for the rollup's full 365-day retention. See [ClickHouse: rolling back](https://riptide.space/docs/configuration/clickhouse#rollups).
