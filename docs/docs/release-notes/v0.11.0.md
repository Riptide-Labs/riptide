## Highlights

**Rollups carry the sampling rate** (#585, closes #470). `SUM(bytes * samplingInterval)` now means the same thing against a rollup as against raw `flows`. Sampling-corrected volume was previously unanswerable beyond the raw table's 30-day retention, because the rollups that survive to 365 days did not carry the rate.

**Rollups change shape on a live deployment** (#582). A rollup can gain a dimension in place, with no aggregation gap. The alternative was dropping and recreating the materialized view, measured at 0.44% flow loss under continuous insert.

**IPFIX reads the sampling rate exporters advertise** (#590, closes #589). An IPFIX exporter that states its rate in a sampler options record, which is what Juniper inline-jflow does, was recorded as unsampled and under-reported by its full sampling rate. NetFlow v9 already correlated these records; IPFIX now does too.

## Fixes

- A `file://…#key` secret reference refuses a key the file declares twice, rather than silently resolving the last declaration (#580, closes #577).

## Upgrading

**Manage-mode deployments** (`manage-schema: true`, the default) repair their rollups on the next start and need nothing.

**Provisioned deployments** (`manage-schema: false`) need two steps, and the second is easy to miss:

```bash
riptide onboard --admin-url <url> --database <db> --tenant <t> --org <o> \
  --writer-secret <ref> --reader-secret <ref>

systemctl restart riptide      # on each collector
```

Which rollups are usable is decided once at startup, so a collector that declined them keeps answering from raw `flows` until it restarts, however complete the repair was. Until both steps run, every query spanning an hour or more falls back to raw `flows` and is silently truncated at raw retention.

**If you receive sampled IPFIX and set a per-receiver `flow-sampling-interval-fallback` to compensate**, the exporter's own advertised rate now outranks that fallback. Where the two disagree, sampling-corrected volume changes. Raw `bytes` and `packets` are untouched, since riptide has never scaled counters at ingest, and `samplingProvenance` moves from `assumed` to `options` for those exporters.

**Rolling back to 0.10.x needs no preparation, and you should not drop the rollup views.**

> **Corrected 2026-08-26.** This paragraph originally said a rollback "requires dropping the rollup views first" and told you to drop the four `_mv` objects. **That was wrong, and following it is what causes the corruption it claimed to avoid.**

An older riptide refuses to shrink a sorting key, so the target keeps every column. It also refuses to narrow the materialized view: `planViewRepair` treats a view selecting columns it does not know as a downgrade and declines it, which `RollupRepairIT.aViewFromANewerVersionIsLeftAloneRatherThanNarrowed` pins against a real server. Versions before v0.10.0 had no `MODIFY QUERY` at all, so they cannot re-point a view either. The wide view stays in place and aggregation continues correctly into columns the running version does not read.

Dropping the views inverts that. A version that declines to build a view for a rollup it considers drifted stops feeding that rollup entirely, and a version old enough to create its own narrow view would point it at the still-wide target, writing the reserved value into a sorting-key column for the rollup's full 365-day retention. See [ClickHouse: rolling back](https://riptide.space/docs/configuration/clickhouse#rollups).
